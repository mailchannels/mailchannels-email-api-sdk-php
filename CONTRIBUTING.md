# Contributing

Thanks for your interest in improving the MailChannels PHP SDK.

## Where work happens

Issues, feature requests, and changes are tracked in Jira under the
[`CLOUD` project](https://mailchannels.atlassian.net/browse/CLOUD). The SDK's
parent epic is [CLOUD-5813](https://mailchannels.atlassian.net/browse/CLOUD-5813).
Before opening a new ticket, search existing ones to avoid duplication.

## Local development

The SDK targets PHP 8.1 or newer.

```bash
composer install
composer test           # PHPUnit (unit + integration suites)
composer phpstan        # static analysis at level max
composer test:coverage  # PHPUnit with Clover + text coverage report
composer check-coverage # enforce 85% coverage threshold against coverage.xml
composer ci             # phpstan + test:coverage + check-coverage
```

For direct PHPUnit runs, use `vendor/bin/phpunit` from the project root, or
pass `tests` or a specific test file. Do not pass the project root as the test
directory (`vendor/bin/phpunit .`), because PHPUnit will discover
`vendor/**/Test.php` files and third-party package tests.

`composer test:coverage` requires a PHP coverage driver. Install
[`pcov`](https://github.com/krakjoe/pcov) (faster) or `xdebug` locally;
CI installs `pcov` automatically.

Tests must pass and PHPStan must remain clean before any change is merged.
CI (Bitbucket Pipelines, see `bitbucket-pipelines.yml`) runs `composer ci`
plus a PHP 8.1–8.4 test matrix on every pull request and on merges to
`main`.

### Running a single test

```bash
vendor/bin/phpunit --filter VerifierTest
```

### Adding dependencies

Keep the runtime dependency surface to PSR interfaces and `php-http/discovery`.
Anything more requires explicit justification in the change description —
applications that pull in the SDK should not transitively acquire surprising
libraries. Test and tooling dependencies belong in `require-dev`.

## Style

- PSR-1 + PSR-12 coding standard.
- `declare(strict_types=1);` at the top of every PHP file.
- Prefer constructor property promotion; mark properties `readonly` when
  they don't change after construction.
- Use named arguments at call sites when the constructor has more than
  three optional parameters — particularly for `EmailParams` and
  `Personalization`.
- PHPDoc `array<string, mixed>` (single space after `@param`) for typed
  arrays. PHPStan level max enforces this.

## Testing

- Every public method needs at least one test.
- Bug fixes ship with a regression test that fails without the fix.
- Use the in-package fixtures in `tests/Support` (notably
  `MockHttpClient` and `RecordingLogger`) so unit tests don't make real
  network calls.

## Logging

The SDK uses PSR-3 (`Psr\Log\LoggerInterface`). When adding new log
statements, pick the level per the
[MailChannels Application Logging Standards](https://mailchannels.atlassian.net/wiki/spaces/DEV/pages/8553901):

- `error`: a request failed and the caller cannot recover automatically.
- `warning`: unexpected behaviour the SDK silently worked around.
- `info`: an action was performed at the caller's request (sends,
  deletions, configuration changes).
- `debug`: per-request diagnostic detail useful only when troubleshooting.

Never log API keys, request bodies, or attachment contents.

## Spec conformance

The SDK is generated by hand from the published OpenAPI spec at
[`docs.mailchannels.net/email-api.yaml`](https://docs.mailchannels.net/email-api.yaml).
When the spec changes:

1. Re-read the changed schema sections verbatim — don't rely on summaries.
2. Update enums, value objects, and validation in the SDK.
3. Update `docs/API_COVERAGE.md` if any routes were added or removed.
4. Add or adjust tests around the changed contract.

## Releasing

Releases are cut by the SDK maintainer. The release process bumps the
version in `src/Version.php` and `CHANGELOG.md`, tags the commit, and
publishes to Packagist. Contributors do not need to manage version bumps.
